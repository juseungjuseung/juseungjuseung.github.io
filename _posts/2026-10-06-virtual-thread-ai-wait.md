개발 중인 서비스의 채팅 API는 사용자 메시지를 AI 서버에 보내고, 답변을 받아 돌려준다. 로그를 확인해 보니 AI 응답을 기다리는 데 평균 13초가 걸렸다.

대기 시간이 긴 요청에서 가상 스레드가 어떤 차이를 만드는지 확인하려고 부하 테스트를 진행했다.

## 예상 처리량

이 API는 동기 방식으로 동작해 AI 응답을 기다리는 동안에도 Tomcat 스레드를 점유한다. 가상 스레드 적용 전, Spring Boot 기본 설정의 Tomcat 스레드는 최대 200개다.

초당 요청 수에 처리 시간을 곱하면 동시에 필요한 스레드 수를 대략 구할 수 있다.

{% include charts/thread-wait.html %}

AI 응답에 13초가 걸리면, 초당 15건을 처리하는 데 약 195개의 스레드가 필요하다. 최대 스레드 수인 200개에 가깝다. 반면 20ms 만에 끝나는 조회 요청은 초당 100건을 처리해도 약 2개면 된다. 같은 요청 수라도 처리 시간이 길수록 필요한 스레드가 많아진다.

이번 테스트에서 설정한 평균 대기 시간은 12.9초다. 다른 처리 시간을 제외하면, 스레드 200개로 처리할 수 있는 채팅 요청은 **초당 약 15.5건**이다.

`200개 ÷ 12.9초 ≈ 15.5건/초`

## 가상 스레드란

가상 스레드는 JVM이 관리하는 가벼운 스레드다. 기존 플랫폼 스레드는 OS 스레드와 하나씩 연결되지만, 여러 가상 스레드는 적은 수의 OS 스레드를 번갈아 사용한다. I/O 대기 중에는 다른 가상 스레드가 OS 스레드를 사용할 수 있어, 외부 API 응답을 기다리는 요청이 많을 때 유리하다.

## 테스트 설계

기존 부하 테스트 시나리오에 가상 스레드를 적용했지만, 성능 차이는 크지 않았다.

이 시나리오에서는 전체 요청의 89%가 관리자 민원 목록 조회였다. 초당 75건을 보내는 동안에도 Tomcat 스레드는 200개 중 최대 12개만 사용됐다. 요청 처리 스레드에는 여유가 있었고, 가상 스레드 적용 전후 모두 DB 커넥션이 병목이었다.

그래서 AI 응답을 기다리는 채팅 API로 테스트 대상을 바꿨다. 요청량을 단계적으로 늘리면서 처리량과 응답 시간을 비교했다.

### AI 응답 시간 측정

먼저 운영 서버 로그에서 9월 23일부터 10월 6일까지 기록된 AI 응답 시간을 집계했다. 사진이 첨부된 요청 5건은 응답에 15~55초가 걸렸고, 이번 테스트에서는 제외했다.

| 경로 | 건수 | 평균 | p50 | p90 |
| --- | ---: | ---: | ---: | ---: |
| 민원 대화 | 31 | 13.3초 | 13.0초 | 19.6초 |
| 규정 질의 (문서 검색) | 9 | 11.9초 | 10.8초 | 15.3초 |

부하 테스트에서는 실제 AI 서버 대신 Stub 클라이언트를 사용했다. 실제 서버를 호출하면 실행할 때마다 응답 시간이 달라지기 때문이다. Stub은 운영 로그를 기준으로 정한 시간만큼 기다린 뒤 고정된 답변을 반환한다.

대기 시간은 요청마다 다르게 설정했다. 운영 로그를 참고해 짧게 끝나는 요청과 오래 걸리는 요청이 모두 나오도록 구성했다.

### 테스트 시나리오

- **채팅 전송**: 입주민 100명이 새 대화를 시작한다. 요청은 민원 대화 70%, 규정 질의 30%로 구성했다. 초당 요청 수는 8건부터 12, 16, 20, 24, 32건으로 늘렸다. 각 단계에서는 20초에 걸쳐 요청량을 높이고, 해당 부하를 90초간 유지했다.
- **대화 목록 조회**: AI를 호출하지 않는 가벼운 조회 요청이다. 초당 5건으로 고정해, 채팅 요청의 증가가 다른 API에도 영향을 주는지 확인했다.

민원 대화 70%, 규정 질의 30%를 기준으로 계산한 평균 대기 시간은 약 12.9초다. 예상 처리량이 초당 15.5건이므로, 초당 16건부터는 요청이 대기할 것으로 예상했다.

### 시간 측정

응답 시간은 서버와 사용자 측에서 각각 측정했다. 서버에서는 Spring Boot의 요청 처리 시간을, 사용자 측에서는 k6의 응답 시간을 기록했다.

### 테스트 환경

노트북 한 대에서 애플리케이션, MySQL, Grafana, k6를 모두 실행했다. 두 테스트는 같은 환경에서 진행하고, 가상 스레드 설정만 변경했다.

```properties
spring.threads.virtual.enabled=true
```

| 항목 | 구성 |
| --- | --- |
| 장비 | Apple M3 Pro 11코어, 메모리 18GB |
| 런타임 | Java 25.0.3, Spring Boot 4.1.1, Tomcat 최대 스레드 200 (가상 스레드 적용 전) |
| DB | MySQL 8.4.11, HikariCP 최대 10 |
| 부하 도구 | k6 2.1.0, 요청 타임아웃 60초 |
| 모니터링 | Micrometer, OpenTelemetry, Grafana otel-lgtm 0.35.0 (Prometheus, Tempo 포함) |

각 테스트는 DB와 Grafana를 초기화한 뒤 실행했다.

### 처리량과 스레드 사용량

![API별 RPS](/assets/images/virtual-thread/01-rps.png)

가상 스레드 적용 전에는 채팅 처리량이 16.3건/초에서 더 이상 증가하지 않았다. 앞서 계산한 15.5건/초와 가까운 값이다. 이후 k6가 초당 20건, 24건, 32건으로 요청량을 높여도 처리량은 비슷한 수준에 머물렀다.

![Tomcat 스레드](/assets/images/virtual-thread/03-tomcat-threads.png)

채팅 요청량을 초당 16건으로 높인 구간에서 Tomcat 스레드 200개가 모두 사용됐다. 테스트가 끝날 때까지 줄어들지 않았다. 가상 스레드 적용 후에는 Tomcat이 요청마다 가상 스레드를 생성하므로, 이번 테스트에서 기존 스레드 풀 지표는 수집되지 않았다.

![동시 처리 중인 요청과 연결](/assets/images/virtual-thread/04-concurrent-requests.png)

동시에 처리 중인 요청은 최대 201개였고, 서버에 열린 연결은 최대 2,209개였다. 처리량이 늘지 않은 채 연결 수만 증가했다. 가상 스레드 적용 전 테스트에서 애플리케이션의 CPU 사용률은 평균 2.59%, 최대 8.67%였다. 수집된 CPU 사용률은 모두 9% 미만이었지만, 요청이 증가하자 스레드 200개가 모두 사용됐다.

### 서버와 사용자 측의 응답 시간

![대화 목록 조회 평균 응답 시간](/assets/images/virtual-thread/06-browse-k6-vs-server.png)

가상 스레드 적용 전, 서버가 기록한 대화 목록 조회의 평균 응답 시간은 11.3ms였다. 테스트 내내 20ms를 넘지 않았다.

반면 k6가 기록한 평균 응답 시간은 스레드 200개가 모두 사용된 구간부터 증가해 타임아웃 기준인 1분에 도달했다. 서버의 요청 처리 시간에는 스레드를 배정받기 전의 대기 시간이 포함되지 않는다. 실제 처리는 약 11ms 만에 끝나도, 사용자는 처리가 시작되기까지 기다려야 했다.

![채팅 평균 응답 시간](/assets/images/virtual-thread/05-chat-k6-vs-server.png)

채팅 API의 평균 응답 시간도 서버에서는 약 13초였지만, k6에서는 60초까지 증가했다. 요청 처리 전의 대기 시간을 확인하려면 사용자 측 응답 시간도 함께 측정해야 한다.

### 요청 실패율

![k6 성공과 실패](/assets/images/virtual-thread/07-k6-success-fail.png)

부하를 계속 높이자 응답을 60초 안에 받지 못해 실패하는 요청이 발생했다. 전체 채팅 요청의 18.40%가 실패했고, AI를 호출하지 않는 대화 목록 조회도 6.65%가 실패했다.

채팅 요청이 스레드를 모두 사용하면서 대화 목록 조회도 대기하게 됐다. 처리 시간이 짧은 요청도 같은 스레드 풀을 사용하므로 영향을 받았다.

### 가상 스레드 적용

가상 스레드를 적용한 뒤 같은 테스트를 반복했다. 채팅 처리량은 요청량에 따라 증가해 최대 32.2건/초를 기록했다.

동시에 처리 중인 요청은 최대 418개였다. 초당 32건에 평균 대기 시간 13초를 곱한 약 416개와 가까운 값이다.

가상 스레드 적용 후에는 서버와 k6의 응답 시간이 비슷했다. 대화 목록 조회는 서버에서 11.6ms, k6에서 13.0ms였고, 채팅은 양쪽 모두 13.0초였다. 실패한 요청은 없었다.

| 항목 | 가상 스레드 적용 전 | 가상 스레드 적용 후 |
| --- | ---: | ---: |
| 채팅 처리량 최대 | 16.3건/초 | 32.2건/초 |
| 채팅 실패율 (60초 타임아웃) | 18.40% | 0% |
| 채팅 응답 p95 (k6) | 59.99초 | 20.71초 |
| 대화 목록 조회 실패율 | 6.65% | 0% |
| 대화 목록 조회 응답 p95 (k6) | 59.94초 | 21.42ms |
| 동시에 처리 중인 요청 최대 | 201 | 418 |

## 자원 사용량

![JVM 힙과 스레드](/assets/images/virtual-thread/08-jvm.png)

OS 스레드(플랫폼 스레드)는 최대 225개에서 38개로 줄었지만, 최대 힙 사용량은 256MiB에서 378MiB로 늘었다. 동시에 처리하는 요청이 두 배 이상 늘어난 영향으로 보인다.

![HikariCP 커넥션](/assets/images/virtual-thread/09-hikari.png)

동시에 사용한 DB 커넥션은 최대 3개에서 9개로 증가했다. 풀 크기는 10개였고, 커넥션 대기는 발생하지 않았다.

트레이스에서 확인한 대화 시작 요청의 트랜잭션은 AI 호출 전후로 분리돼 있었다. AI 응답 대기 중에는 DB 커넥션을 점유하지 않았다.

DB 커넥션을 점유한 채 AI 응답을 기다리는 구조라면, 커넥션 풀 크기가 동시 처리량을 제한할 수 있다. 가상 스레드를 적용할 때는 트랜잭션 범위와 커넥션 사용 시간도 확인해야 한다.

## 테스트의 한계

- 노트북 한 대에서 애플리케이션, DB, Grafana, k6를 함께 실행했고, 각 조건은 한 번씩만 측정했다.
- 32.2건/초는 이번 시나리오에서 확인한 최대 처리량이다. 가상 스레드 환경의 최대 처리 성능을 찾을 때까지 부하를 높인 것은 아니다.
- Stub은 애플리케이션 안에서 대기하므로, 실제 AI 서버의 동시 요청 처리 한도와 HTTP 클라이언트의 커넥션 풀 제약은 반영하지 못했다.

## 결론

이번 테스트에서는 가상 스레드 적용 후 최대 채팅 처리량이 16.3건/초에서 32.2건/초로 증가했고, 채팅 실패율은 18.40%에서 0%로 줄었다. AI 응답 대기 시간을 줄인 것이 아니라, 응답을 기다리는 동안 더 많은 요청을 처리할 수 있게 된 결과다.

**외부 API 호출처럼 I/O 대기가 길고 동시 요청이 많은 작업에서는 가상 스레드 적용이 유의미하다.** 특히 대기 중인 요청이 플랫폼 스레드를 점유해 처리량이 제한되는 경우에 도움이 된다. 이번 테스트는 실제 AI 호출 대신 Stub으로 대기 시간을 재현해 이 차이를 확인했다.

반면 **CPU 연산이 대부분인 CPU-bound 작업은 가상 스레드를 늘려도 연산 속도가 빨라지지 않는다.** 동시에 연산할 수 있는 양은 CPU 코어 수에 제한되기 때문이다. [JEP 444](https://openjdk.org/jeps/444)에서도 가상 스레드의 처리량 개선 효과를 동시 작업이 많고 대기 시간이 긴 경우로 설명한다.

DB 커넥션이나 외부 API의 처리 한도가 병목인 경우에도 가상 스레드만으로 해결되지는 않는다. 처음 진행한 조회 위주의 테스트에서도 DB 커넥션이 병목이어서 성능 차이가 크지 않았다. 적용 여부를 결정하려면 요청이 어디에서 대기하는지 먼저 확인해야 한다.

실제 서비스에 적용하기 전에는 AI 서버의 동시 요청 한도와 HTTP와 DB 커넥션 풀 크기를 점검할 예정이다. 같은 조건으로 테스트를 반복하고, 서버와 사용자 측 응답 시간을 함께 비교하려고 한다.
